## 1. Objetivo del día

Continuar el diseño de un experimento que permita comprobar si la **organización de los caracteres** influye en los errores de un modelo de lenguaje al contar las apariciones de un patrón dentro de una cadena.

El reto exige contar **todas las apariciones, incluidas las solapadas**.

## 2. Hipótesis

- **Hipótesis principal (H1):** Las cadenas alternadas producirán una mayor tasa de errores que las cadenas agrupadas al contar apariciones de patrones.
- **Hipótesis nula (H0):** No se observará una diferencia sistemática en la tasa de errores entre ambos tipos de cadenas.

Las hipótesis aún no se han contrastado. La posible influencia de la tokenización o de otros mecanismos internos es una explicación tentativa, no una conclusión.

## 3. Grupos y cadenas iniciales

Conservamos las cuatro cadenas de partida, todas de 10 caracteres y compuestas por cinco `A` y cinco `B`.

| Grupo | Código | Cadena | Organización |
|---|---|---|---|
| A | A1 | `AAAAABBBBB` | Agrupada, comienza por A |
| A | A2 | `BBBBBAAAAA` | Agrupada, comienza por B |
| B | B1 | `ABABABABAB` | Alternada, comienza por A |
| B | B2 | `BABABABABA` | Alternada, comienza por B |

Estas cadenas serán el punto de partida; **no serán necesariamente las únicas**. Se incorporarán otras longitudes para ampliar la exploración.

## 4. Restricciones del reto que debemos respetar

- Las cadenas tendrán **entre 10 y 50 caracteres**, utilizando exclusivamente `A`, `B` y `C`.
- Los patrones tendrán **entre 2 y 4 caracteres**, también formados por `A`, `B` y `C`.
- Un **caso de prueba** consiste en una combinación concreta de cadena y patrón. Una misma cadena puede intervenir en varios casos si cambia el patrón.
- Deben prepararse **al menos 10 casos diferentes**; no es un máximo.
- Cada caso debe ejecutarse **al menos 3 veces de manera independiente**, sin contexto previo.
- Se utilizará el **prompt estandarizado del reto** para las pruebas principales, cambiando únicamente cadena y patrón.
- El modelo evaluado no utilizará herramientas externas ni ejecutará código para resolver el conteo.
- Se documentarán las respuestas, configuraciones y evidencias, y se prepararán los resultados en el formato requerido por el reto.

## 6. Cómo construiremos los casos

La idea es desarrollar un **generador en Python** que:

1. Genere cadenas candidatas con las longitudes y organizaciones seleccionadas.
2. Genere o seleccione patrones de entre 2 y 4 caracteres.
3. Calcule exactamente el número de apariciones de cada patrón, **incluyendo los solapamientos**.
4. Compruebe que las combinaciones cumplen las restricciones del reto.
5. Seleccione y guarde veinte casos diferentes: diez para cada grupo.
6. Exporte los casos y sus soluciones verificadas para facilitar las pruebas y el análisis.

**Decisión metodológica:** no fijaremos obligatoriamente la misma cantidad de apariciones en todos los casos. Permitiremos que varíe y la registraremos para analizar si también influye en los resultados.

Esto introduce una precaución: si un grupo acumula patrones con muchas apariciones y el otro con pocas, una diferencia de errores **no podría atribuirse sin más a la organización**. Compararemos casos de longitud semejante y documentaremos el número real de apariciones; el equilibrio exacto entre los casos todavía queda por diseñar.

### Ejemplo de solapamiento

- Cadena: `ABABA`
- Patrón: `ABA`
- Apariciones correctas: **2** (posiciones 1–3 y 3–5).

El verificador deberá contar ambas.

## 7. Dos modalidades de ejecución

### Modalidad automática: Python + API de OpenAI

- Python enviará cada caso al modelo mediante solicitudes independientes.
- Cada solicitud incluirá el prompt oficial, la cadena y el patrón, **sin incorporar la respuesta correcta** ni respuestas previas.
- Se registrarán el modelo utilizado, la configuración, la respuesta recibida y la evidencia disponible.
- Python comparará la respuesta obtenida con el resultado calculado previamente.

### Modalidad manual: interfaz de ChatGPT

- Realizaremos tres pruebas independientes de cada caso, usando **un chat nuevo sin contexto previo para cada ejecución**.
- Emplearemos el mismo prompt oficial y los mismos casos.
- Registraremos las respuestas y conservaremos evidencias de cada ejecución.

**Precaución:** la API y la interfaz no necesariamente ofrecen un modelo o una configuración idénticos. Cualquier diferencia entre modalidades se interpretará teniendo en cuenta este posible factor.

## 8. Datos y análisis previstos

Para cada ejecución registraremos, como mínimo:

- Identificador del caso y grupo experimental.
- Longitud y contenido de la cadena.
- Patrón, longitud y número correcto de apariciones.
- Modalidad (`API` o `manual`), modelo y configuración disponible.
- Número de ronda y respuesta del modelo.
- Indicación de acierto/error y evidencia de la ejecución.

La medida principal será la **tasa de error**:

\[
\text{Tasa de error (\%)} = \frac{\text{respuestas incorrectas}}{\text{ejecuciones realizadas}} \times 100
\]

Se compararán las tasas de error de las cadenas agrupadas y alternadas **dentro de cada modalidad**. Posteriormente se examinará si ambas modalidades muestran resultados compatibles, además de explorar el posible efecto de la longitud del texto, la longitud del patrón y el número de apariciones.

Tener más casos amplía la exploración, pero **no garantiza por sí solo una comparación causal**: será necesario atender a las demás variables.
